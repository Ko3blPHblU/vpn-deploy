# vpn-deploy — автодеплой VPN-сервиса I→O (Remnawave)

Набор скриптов для развёртывания архитектуры «входные ноды в РФ → выходные ноды
за рубежом» под управлением панели [Remnawave](https://remna.st).
Цель — деплой одного сервера за 3–5 минут: все реквизиты в `node.conf`,
всё недостающее скрипт спрашивает интерактивно.

За основу взят [proxy-deploy-public](https://github.com/Ko3blPHblU/proxy-deploy-public):
единый конфиг-файл, идемпотентность, секреты не печатаются в консоль.

Архитектура и план внедрения — в заметках vault:
`Архитектура/Архитектура VPN-сервиса — проект.md`, `Архитектура/План внедрения VPN-сервиса.md`.

## Файлы

| Файл | Назначение |
|---|---|
| `bootstrap.sh` | Первичный скрипт чистого VPS: обновления, пользователь с SSH-ключом, ufw, fail2ban, автообновления безопасности, sysctl (ip_forward, BBR) |
| `deploy-node.sh` | Главный диспетчер ролей: `panel` / `exit` / `entry` |
| `gen_entry_profile.py` | Генератор config-profile Remnawave для входной ноды (каскад на выходы, маршрутизация RU→DIRECT). Вызывается автоматически из `deploy-node.sh` |
| `node.conf.example` | Аннотированный шаблон конфигурации |

## Поток на сервере (3–5 минут)

```bash
# 0. Заранее на ПК: скопировать node.conf.example → node.conf и заполнить
#    под роль сервера; секреты не коммитить.

# 1. Подключиться по SSH (root), поставить скрипты:
apt-get update -qq && apt-get install -y -qq git curl
git clone https://github.com/<user>/vpn-deploy.git
cd vpn-deploy

# 2. Скопировать заранее заполненный конфиг с ПК:
#    (на ПК) scp node.conf root@SERVER:/root/vpn-deploy/node.conf

# 3. Первичная подготовка (~1–2 мин):
bash bootstrap.sh
#    Проверить новое SSH-подключение, не закрывая старое!

# 4. Деплой роли (~2–3 мин):
bash deploy-node.sh

# 5. Получить реквизиты:
#    panel: /opt/remnawave/credentials.txt  (ссылка первого входа со «стуком»)
#    exit:  статус ноды — в панели (Nodes)
#    entry: /opt/vpn-deploy/entry-config-profile.json → в Config Profiles панели
```

Повторный запуск `deploy-node.sh` безопасен: существующие `.env` и compose
не перезаписываются, секреты не перегенерируются.

## Роли

### panel (1 сервер)

Ставит Docker, скачивает официальные `docker-compose-prod.yml` и `.env.sample`
из `remnawave/backend`, заполняет `.env` случайными секретами
(`APP_SECRET`, `METRICS_PASS`, `WEBHOOK_SECRET_HEADER` — ровно 64 символа,
`POSTGRES_PASSWORD` + та же в `DATABASE_URL`), поднимает панель, PostgreSQL,
Valkey и Caddy (HTTPS + автовыпуск сертификата).

Панель слушает только `127.0.0.1`; снаружи — Caddy на 80/443 с «стуком»:
первый вход по ссылке `https://PANEL_DOMAIN/?rw=СЕКРЕТ`, дальше cookie
`rw_gate` на 30 дней; без стука — обрыв соединения (панель не светится
сканерам). **Первый зарегистрированный пользователь = супер-админ** — открыть
ссылку сразу после деплоя.

Требования: домен с A-записью на сервер, минимум **2 vCPU / 2 ГБ RAM**
(требование Remnawave; на 1 ГБ не ставить). В бюджетной схеме панель
совмещается с первой выходной нодой на Hetzner (4 ГБ) либо ставится на
апгрейднутый вход VDSina 2 ГБ.

### exit (выходные ноды, EU)

Ставит Docker и запускает `remnawave-node` из compose, сгенерированного
панелью (`REMNA_NODE_COMPOSE_B64`). Compose уникален для каждой ноды
(внутри секретный ключ) — генерируется в панели при создании ноды.

### entry (входные ноды, РФ)

То же, что `exit`, плюс `gen_entry_profile.py` собирает config-profile панели:
по одному входу VLESS+XHTTP+Reality на каждый выход (порты 443/1443),
outbounds на выходы из `EXIT*_LINK`, маршрутизация: приватные адреса,
`geosite:category-ru`, домены `.ru/.su/.рф` и `geoip:ru` → DIRECT, остальное —
через выбранный выход. Ключи Reality генерируются локально (openssl X25519),
клиентские ссылки — в `entry-config-profile.json.links.txt` для самопроверки;
боевым клиентам конфиги раздаёт подписка панели.

## Порядок развёртывания сервиса

1. **panel** — после деплоя открыть ссылку из `credentials.txt`, создать
   админа, создать «транзитного» пользователя.
2. **exit** ×2 — создать ноды в панели, скопировать compose в конфиги,
   задеплоить, получить vless-ссылки транзитного пользователя на каждый выход.
3. **entry** ×2 — вписать `EXIT1_LINK`/`EXIT2_LINK` в конфиги, задеплоить,
   вставить сгенерированный JSON в Config Profiles, назначить нодам
   и пользователям.
4. **Опционально**: страница подписок на отдельном домене — создать API-токен
   (Settings → API Tokens), вписать `SUB_DOMAIN` + `REMNAWAVE_API_TOKEN`
   в конфиг панели, перезапустить `deploy-node.sh` (добавит контейнер
   `remnawave/subscription-page` и блок в Caddyfile).

## Безопасность

- `node.conf`, `/opt/vpn-deploy/node.conf`, `credentials.txt`, `.env`, Caddyfile —
  права 600/700, только root. `node.conf` **не коммитить** (в Git — только
  `node.conf.example`).
- Секреты не выводятся в консоль; лог деплоя — `/opt/vpn-deploy/deploy-node.log`.
- SSH остаётся на 22 порту; вход по паролю отключается только при заданном
  `ADMIN_PUBKEY` и валидируется `sshd -t`.
- Резервное копирование: `/opt/remnawave` (БД в volume `remnawave-db-data` —
  `pg_dump` по cron, см. план внедрения).

## Известные ограничения / roadmap

- Транзит I→O только VLESS+Reality: xray-core не умеет Hysteria2-outbound.
  Hysteria2 на входе (маскировка под QUIC) — отдельным шагом позже.
- Страница подписок требует API-токен, который существует только после первого
  входа в панель, — деплой панели двухпроходный (это by design).
- Ссылки в `*.links.txt` содержат `<IP_ЭТОЙ_НОДЫ>` — подставляется вручную,
  нужны только для теста; клиенты работают через подписку.
- `gen_entry_profile.py` требует python3 и openssl (ставятся автоматически,
  если отсутствуют).
